## Общее описание

Репозиторий содержит единственный проект — `laba_8_on_condition`, учебную лабораторную работу на Python. Это простое веб-приложение "на чистом" `http.server` (без Flask/Django), которое хранит в памяти пользователей и курсы валют, отдаёт несколько HTML-страниц через Jinja2-шаблоны и позволяет пользователю подписываться на валюты. В репозитории один коммит («Add files via upload»), то есть история разработки не сохранена — файлы были загружены разом.

Структура проекта: `main.py` — точка входа и HTTP-обработчик; `models/` — четыре доменных класса (`Author`, `App`, `User`, `Currency`, `UserCurrency`) с хранением данных в classmethod-хранилищах на уровне класса; `utils/currencies_api.py` — обращение к публичному API курсов ЦБ РФ (`cbr-xml-daily.ru`); `templates/` — четыре HTML-шаблона; `tests/` — три файла с тестами на pytest/unittest.

## Модели данных

Классы `Author` и `App` — простые value-объекты с приватными полями и валидирующими сеттерами (например, версия приложения обязана быть в формате `X.Y.Z`, группа автора — ровно 5 символов). `User` и `Currency` устроены как мини-ORM поверх словаря класса: у каждого есть `create`, `find_by_id`, `find_by_char_code`/`find_by_email`, `get_all`, инкрементальный `id`, и валидация полей через property-сеттеры (email должен содержать `@`, курс валюты — положительное число, символьный код валюты приводится к верхнему регистру). `UserCurrency` реализует связь многие-ко-многим между пользователями и валютами: подписку, отписку, проверку подписки и историю операций с таймстампом, а также заглушку `get_currency_trend`, которая генерирует случайный тренд курса вместо реальных исторических данных.

При импорте `models/user.py` и `models/currency.py` сразу же создают тестовые данные: пять захардкоженных пользователей и полный список валют, полученный живым запросом к API ЦБ РФ. Так же в `UserCurrency` при импорте сразу создаётся пять тестовых подписок. То есть демо-данные — часть кода моделей, а не отдельный сценарий инициализации.

## Работа с внешним API валют

`utils/currencies_api.py` реализует `get_currencies` — обёртку над `requests.get` к `https://www.cbr-xml-daily.ru/daily_json.js` с обработкой сетевых ошибок (`ConnectionError`), некорректного JSON (`ValueError`) и отсутствующих валют (`KeyError`), плюс поддержкой подстановки тестового ответа через параметр `test_response` для тестирования без сети. Поверх неё построены `get_all_currencies_data` (нормализует ответ в список словарей для создания объектов `Currency`) и `update_all_currencies` (обновляет существующие валюты или создаёт новые). Модуль в целом неплохо продуман с точки зрения обработки ошибок, но именно эта функция вызывается на этапе импорта `models/currency.py` — из-за этого весь модуль `models`, а вместе с ним и всё приложение, не может быть загружен без доступа к внешнему API ЦБ РФ. Это подтвердилось при попытке запустить тесты в этом окружении: импорт `models` упал с `ConnectionError`, так как сеть до `cbr-xml-daily.ru` недоступна, и все тесты (`test_control_main.py`, `test_model.py`) не смогли даже начать выполняться. После точечной подмены `get_all_currencies_data` (мок вместо реального сетевого вызова) приложение и сервер отработали корректно.

## Веб-сервер и маршруты

`main.py` поднимает `HTTPServer` на `localhost:8080` и обрабатывает пять маршрутов через `if/elif`-цепочку в `do_GET`: `/` (информация о приложении), `/author` (информация об авторе — рендерится тем же шаблоном `index.html`, но с другим значением `flag`), `/currencies` (таблица всех валют), `/users` (таблица пользователей) и `/user?id=<N>` (карточка конкретного пользователя с его подписками; этот маршрут реализован отдельным циклом по всем пользователям с сравнением полной строки пути, а не разбором query-параметра).

Проверка запуском сервера с замоканным сетевым вызовом показала, что все пять маршрутов рендерятся и отдают ожидаемое содержимое (например, `/user?id=0` корректно показывает список подписанных валют). Но в обработчике `do_GET` нет ветки `else`/404 для неизвестных путей: если запрошен любой маршрут, не входящий в перечисленные (включая типовой автоматический запрос браузера `/favicon.ico`), переменная `result` остаётся неприсвоенной, и на строке `self.wfile.write(bytes(result, "utf-8"))` падает `UnboundLocalError`. Поскольку заголовки `200 OK` к этому моменту уже отправлены, клиент реально получает ответ `200` с пустым телом, а в консоли сервера остаётся необработанное исключение — это подтверждено прямым запуском сервера и обращением к `/favicon.ico` и `/nonexistent` в этом окружении.

Также обнаружено, что шаблон `currencies.html` ожидает переменную `current_time`, но `main.py` при рендере `/currencies` её не передаёт — Jinja2 в этом случае не выбрасывает ошибку, а тихо подставляет пустую строку, из-за чего в реальном выводе страницы после «Текущее время:» ничего не отображается (тоже проверено прямым запросом к работающему серверу).

В файле присутствует закомментированный блок `do_POST` с логикой регистрации и логина через `User.create`/`User.authenticate`, но метод `authenticate` в классе `User` не реализован, а сама регистрация отключена — то есть аутентификация задумывалась, но не была доведена до рабочего состояния в этой версии.

## Шаблоны

Шаблоны написаны на чистом HTML с использованием условий и циклов Jinja2, без внешних CSS-фреймворков, стили инлайновые в `<style>`. Обнаружена мелкая вёрстка-неточность в `users.html`: строка `<tr>` после `<td>` с именем пользователя не закрыта (`<tr>` вместо `</tr>`) внутри цикла `for`, из-за чего структура таблицы становится вложенной некорректно (браузеры обычно исправляют это автоматически, но валидным HTML это не является).

## Тесты

Тестовый набор состоит из трёх файлов. `test_model.py` — модульные тесты на unittest для всех классов моделей (`Author`, `App`, `User`, `Currency`, `UserCurrency`), с явной очисткой приватных class-level хранилищ в `setUp` — сами тесты написаны аккуратно и по значительной части бизнес-логики (валидация полей, поиск, подписки, история) дают хорошее покрытие. `test_get_currency.py` тестирует `get_currencies`: часть тестов использует внедрение тестовых данных через `test_response` (что делает их устойчивыми к реальной сети), но часть — обращаются к настоящему API ЦБ РФ или к `https://www.google.com` (в тесте `test_invalid_value_error`, чтобы спровоцировать `ValueError` из-за не-JSON ответа), что делает эти тесты интеграционными, а не модульными: они зависят от доступности интернета и от третьих сторон, и в данном окружении (без доступа к сети) не могут быть выполнены. Там же тест `test_get_valid_currencies` содержит захардкоженный диапазон допустимых значений курса USD (51–121 руб.), который со временем неизбежно устареет. `test_control_main.py` поднимает реальный HTTP-сервер в отдельном потоке и проверяет все пять маршрутов через живые HTTP-запросы — из-за описанной выше проблемы с импортом `models` (сетевой вызов при загрузке модуля) все тесты в этом файле в данном окружении не смогли запуститься уже на этапе сборки (`ERROR collecting`), а не из-за ошибок в самой тестируемой логике.

## Итоговая оценка

Проект в целом демонстрирует связный, самодостаточный пример небольшого веб-приложения: слой моделей с валидацией, интеграция с внешним API, шаблонизация и тесты на разных уровнях (модульные и через реальный HTTP-сервер) присутствуют и в основном работают корректно — это было проверено непосредственным запуском сервера и обращением к каждому маршруту. Главная системная проблема — жёсткая связка инициализации данных с сетевым вызовом на этапе импорта `models`, из-за которой всё приложение (включая тесты, не имеющие отношения к валютам) не может быть запущено без доступа к внешнему API; в паре с отсутствием обработки 404 это означает, что даже штатный запрос браузера к `/favicon.ico` роняет обработчик с необработанным исключением. Остальные найденные недочёты (не передаваемая в шаблон `current_time`, незакрытый тег `<tr>`, тесты с обращением к реальным внешним сервисам и захардкоженным диапазоном курса) — менее критичны, но стоит иметь в виду при доработке.
